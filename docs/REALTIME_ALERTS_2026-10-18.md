# 실시간 감지·텔레그램 주문 알림 점검 및 개선 (2026-10-18)

작업지시서("전 종목 실시간 감지 및 텔레그램 매수·매도 알림 개선")의 1~4차 결과다. **병합·배포·PC 적용은 하지 않았다**(`CLAUDE.md`: quant-autotrade는 사용자 별도 승인 전 병합·운영 반영 금지).
실제 주문을 내는 PC 엔진(`live_engine.py`)과 로컬 봇의 판단·주문 코드는 변경하지 않았다. 실제 주문을 발생시키는 테스트는 하지 않았다.

## 1차 — 실계좌 매수·매도 텔레그램 알림

### 원인 (실제 경로 확인)
- 실제 주문을 내는 것은 저장소 밖 PC 전용 `live_engine.py`이고 장부는 `live_orders.db`(`intents`·`positions`)다(`quant-autotrade/docs/LIVE_EXIT_RULES_2026-10-16.md`).
- 텔레그램 감시자(`tg_monitor.py`)는 로컬 봇의 `autotrader.db`(감시 종목 손절·익절)만 읽었다. **엔진이 낸 매수·매도 주문은 텔레그램에 전혀 나오지 않았다.** 이것이 "무엇을 샀고 팔았는지 알림에 안 나온다"의 원인이다. (로컬 봇이 직접 내는 매도 `SELL_SENT`는 알림이 있었지만 수량·시각이 빠져 있었다.)
- 텔레그램 토큰·전송 경로는 PC 봇(`main.py`의 `tg-sender`/`tg-monitor` 스레드)이며, 엔진과 별도 프로세스·스레드라 전송 실패가 주문·손절·익절 판단을 늦추지 않는다.

### 변경 (알림 전용, 읽기 전용)
| 파일 | 내용 |
|---|---|
| `local_bot/tg_live_orders.py`(신규) | 장부 `intents`를 읽기 전용으로 읽고(오늘 것만), 단계(주문 요청·증권사 접수·일부/전량 체결·거부·전송 실패·상태 확인 필요)를 판정하고 알림 문구를 만든다 |

알림 항목: 종목명·종목코드(이름 조회 실패해도 코드 표시), 주문 시각(KST, 초), 주문 수량, 주문가(매수)·판정가(매도, 시장가라 체결가 아님), 주문금액(주문가 기준·체결금액 아님 명시), 확인된 체결 수량·평균가·체결금액(출처 표기), 매수 사유(`ENTRY`·검색기 이름), 매도 사유(`STOP_3`·`STOP_EMERGENCY`·`TRAIL_2_5` 한글 풀이), 실현손익(**매수·매도 체결가가 모두 확인된 경우에만**, 비용 제외 명시, 아니면 `확인 불가`), 장부 상태 코드·주문번호 끝 4자리.

### 지켜진 원칙과 미확인
- 체결 확인은 사용자가 남기는 `order_fills.json`(키움 당일매매일지)이 있을 때만 `일부/전량 체결`로 표시한다. 접수(`ACK`)만으로는 체결 완료라고 쓰지 않으며 "접수일 뿐 체결 확인이 아닙니다"를 적는다. 확인되지 않은 가격·손익은 계산하지 않는다.
- **미확인**: 장부 `state`의 `ACK` 외 값(거부·실패·부분체결 표기), `note` JSON의 검색기 이름 키. 그래서 알 수 없는 상태는 원문 코드를 그대로 보여 주고 `상태 확인 필요`로 쓴다(체결로 단정하지 않음). 검색기 이름을 못 찾으면 `검색기 이름 기록 없음`이라고 적는다. 실제 장부에서 값이 확인되면 `tg_live_orders.base_stage`·`SCANNER_KEYS`만 고치면 된다.
- 텔레그램 전송 실패 시 장부는 읽기만 하므로 엔진에 영향이 없다(테스트: 알림 적재 예외에도 감시자 지속·장부 불변).

## 4차 — 전 종목 실시간 감지의 기술적 가능성과 단계별 도입안
확인된 것(저장소 코드·운영 실측)
- KIS: 허브가 앱키당 세션 1개에 등록 41건을 시도해 41건 모두 성공·거부 0(운영 실측). 41건 **이상**이 가능한지, 세션·계정 수 정책은 **미확인**(허브 주석도 "KIS 문서로 확인하지 못함"). 저장소에서 확인된 KIS 실시간은 종목별 체결가·호가 구독이며 **전체 시장 스트림은 확인하지 못했다**. KIS REST에는 순위(거래량·등락률·체결강도·대량체결건수)와 HTS 조건검색 조회(`psearch_title`/`psearch_result`) API가 있으나 REST 폴링이며 실시간이 아니다(조건검색 한도·지연은 미검증).
- 키움: 허브 기본 등록 상한 100(`KIWOOM_WS_MAX_CODES`, 문서 미확인 설정값), 등록 1건 정상. **0B 체결의 누적거래량 필드 번호를 확인하지 못해** 지금 키움 허브는 거래량을 넘기지 않는다 - 키움 WebSocket으로는 거래량 속도를 아직 계산할 수 없다.
- 전 종목 약 2,500개: 위 41(KIS)+100(키움, 거래량 미지원) 범위로는 **불가능**. 복수 앱키·세션으로 쪼개는 것은 증권사 정책 준수 여부를 먼저 확인해야 하며 이번에는 시도하지 않았다(미확인).
- e2-micro(1GB) 자원: VM CPU·메모리·네트워크 실측은 운영 접근 없이 할 수 없어 **측정하지 못했다(미확인)**. 현 구조는 별도 프로세스 없이 FastAPI 안 스레드 하나로 30초 순위 4건을 읽는다.
- 수신 지연·누락·끊김: 허브는 5~60초 백오프 재접속, 180초 워치독, 거부 응답 기록을 가진다. 장중 실측 전이다.

단계별 도입안(제안, 승인 필요)
1. (이번 작업) 30초 순위 감시 + 텔레그램 관찰 알림, 감지·알림 시각 기록(`surge_log`).
2. 순위 후보(상위 30~40) + 관심·보유 종목에 한해 KIS `H0UNCNT0` 체결 틱을 허브에 구독해 3분 거래량 속도를 틱으로 계산(순위 API 30초 간격보다 빠름). 등록 자리 41건을 선물·옵션·화면과 나눠 쓰므로 우선순위·예산을 정해야 하고, 누적거래량 필드(체결 응답)는 장중 1회 확인이 필요하다.
3. 키움 `0B`의 누적거래량 필드 확인 후 키움 허브(100)를 후보 감시에 추가.
4. 전 종목 규모는 증권사 문의로 전체 시장 스트림·세션 정책이 확인된 뒤에만 검토. 그전에는 REST 순위·조건검색 폴링과 병행.
- 어느 단계든 기존 30초 감시를 바로 끄지 않고 1~2주 병행하며 누락률·지연을 비교한다.

## 7. 기존 검색기 기준 불일치
- `volume_breakout_scan.py`의 설명은 "전일 거래량의 50%"였고 실제 판정값은 `VOLUME_RATIO_THRESHOLD = 0.3`이었다.
- 이력: 2026-09-22 사용자 지시로 09:10·1.0배 -> 09:05·0.5배(#515), 2026-09-28 "검색 결과가 너무 적어" 0.3배로 완화(커밋 `113019b6`, `docs/WORK_HISTORY.md` 2026-09-28 항목 "전일 거래량 30%·최소 3만 주로 완화", 테스트 `test_volume_breakout_scan.py`도 0.3). 즉 **현재 값 30%는 의도된 변경이고 모듈 주석만 50%로 남아 있었다.**
- 조치: **판정값은 바꾸지 않고** 모듈 설명·주석을 30%로 맞추고 이력을 적었다. 화면 문구는 이 점검에서 50%/30%를 직접 적은 곳을 찾지 못했다(`pattern-scan.js` 확인). 50%를 원하면 별도 지시가 필요하다(이 값은 기존 11개 검색기의 판정 조건이다).
- 구형 09:05 스냅샷(전일의 30%·갭상승)과 실시간 감지(최근 3분 거래량 속도 `PACE_MIN` 0.03 = 전일의 3%/3분)는 기준이 다르며 이번에 임계값을 바꾸지 않았다.

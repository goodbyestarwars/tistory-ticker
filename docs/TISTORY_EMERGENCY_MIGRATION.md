# 티스토리 운영 중단 비상 이전 계획

작성일 2026-11-11 KST. 상태는 계획 수립이며 독립 사이트, 복원 시험, 전환 시간은 미검증이다.

## 1. 목표와 범위

- 자체 도메인에서 홈, 시장 지표, 실시간 종목판, 종목 차트, 검색기, 기존 글과 본문 이미지를 제공한다.
- GitHub master를 코드 원본으로 삼고 로컬 PC에 소스 사본을 만들지 않는다. 소스와 공개용 빌드 입력만 GitHub에서 관리한다.
- 기존 방명록, 댓글, PC통신 글쓰기와 인증은 이관 대상에서 제외한다. 새 메뉴, 모바일 탭, 사이트맵에서 해당 진입점을 정리한다.
- Oracle 공개 API와 기존 GAS를 유지한다. Google VM 실계좌 러너·봇·계정·키·주문 설정은 공개 사이트 전환 범위 밖이다. 공개 빌드에서 운영 제어 페이지 및 주문 기능 진입점을 제외하고 API 인증 경계도 확인한다.
- 공개 서비스 이전과 공급자 데이터 사용권 심사는 구분한다. 정책 통지가 시세·뉴스·이미지 재게시 권한에 관한 것이면 해당 콘텐츠는 숨기고 권리 확인 후 복구한다.

## 2. 발동 기준과 우선순위

| 상황 | 실행 |
|---|---|
| 운영 정책 경고 또는 이전 유예 | 공지 범위와 마감 기록, 최신 백업 확보, 독립 환경 병행 검증 후 전환 |
| 티스토리 접속 불가 또는 스킨 차단 | 자체 도메인 또는 준비된 호스팅 주소에서 상태 안내와 검증된 핵심 화면 먼저 공개. 최신 검증 백업으로 글 복원 |
| GitHub Pages 게시 지연 | 저장소의 검증된 SHA로 Cloudflare Pages 배포 상태 확인. 직전 성공 배포를 유지하고 필요하면 Oracle 정적 서빙으로 전환 |
| Oracle/GAS 장애 동반 | 영향 기능에 갱신 중단·마지막 정상 기준시각 표시. 글과 정적 페이지는 계속 제공. 오래된 데이터를 실시간 값으로 표시하지 않음 |
| 권한·라이선스 문제 | 해당 데이터 또는 게시물만 비활성화하고 운영자 검토. 장소만 바꾸어 제한된 자료를 다시 게시하지 않음 |

운영자는 장애 시작 시각, 영향 범위, 정책 통지, 최신 검증 백업, 커밋 SHA, 배포 ID를 기록한다. 복구 우선순위는 상태 안내와 글 보존, 홈·종목판, 차트·검색기, 기타 위젯 순서다. 목표는 준비된 배포가 있을 때 핵심 화면 2시간 이내, 검증된 글 아카이브 24시간 이내다. 준비 전이나 플랫폼 접근 상실 시 소요시간을 재산정한다.

## 3. 평시 준비와 인수인계

- 운영자와 대체 운영자가 도메인 등록기관·DNS, GitHub 저장소, 티스토리 관리자, Cloudflare, Oracle, GAS의 접근 복구 절차와 담당을 확인한다. MFA 복구 정보와 키는 승인된 비밀 저장소에 보관한다.
- 소유권이 확인된 도메인에 공개 서비스 주소와 API 주소를 구분한다. 현재 API 호스트는 goodbyestar.cloud다. 주소, DNS TTL, TLS 발급 방식, DNS 복원 방법을 기록한다.
- [운영 스킨 반영 목록](SKIN_HTML_PENDING.md)에 따라 GitHub skin.html과 티스토리 관리자 운영본을 비교한다. 운영 전용 수정, 치환자, 위젯, 외부 삽입, PC·모바일 진입점을 표로 기록한다.
- [서비스 지도](SERVICE_MAP.md)와 [API 명세](../API_REFERENCE.md)를 기반으로 화면별 URL, 정적 파일, API·GAS 호출, WebSocket, 데이터 공급자와 인증 요구, 검증 방법을 기록한다.
- GitHub 배포 원본 SHA, 생성 방법, 산출물 해시, 호스팅 배포 ID를 남긴다. 직전 정상 산출물과 DNS 설정 스냅샷을 보관한다.
- 새 글 게시·수정 후 백업을 갱신하고 최소 주 1회 백업 상태를 확인한다. 평시 글 RPO 목표는 7일 이내이며 이전 통지를 받으면 즉시 재백업한다. 월 1회 표본 복원, 분기 1회 핵심 화면 복구 훈련을 권장한다.

## 4. 기존 글과 이미지 백업·복구

1. 티스토리 관리자에서 제공하는 백업을 내려받아 원본 ZIP을 보존하고 SHA-256, 생성일, 크기, 작성자와 보관 위치를 기록한다. 백업에 포함된 게시물 상태와 첨부 범위를 실제 파일로 확인한다.
2. 백업 원본은 승인된 비공개 저장소에 두고 별도 위치에 두 번째 사본을 보관한다. 원본 접근이 막히기 전에 공개 글 목록과 원래 URL을 확인한다. 공개 GitHub에는 공개 권한을 확인한 글과 이미지 또는 빌드 입력만 올린다.
3. 글별 매니페스트를 만든다. 원래 URL, 원본 ID, 새 경로, 제목, 발행일 KST, 수정일, 카테고리·태그, 공개 여부, 본문 해시, 이미지 목록, 변환·검수 상태를 기록한다. 비공개·보호·초안은 공개 결과에서 제외한다.
4. 본문 이미지는 외부 URL 참조와 실제 파일을 대조한다. img src·srcset, 지연 로드 속성, 본문 링크 첨부, 대표 이미지와 캡션을 확인한다. 권한을 확인한 이미지의 실제 파일을 보존하고 해시로 중복을 제거한다. 원본을 구할 수 없는 이미지는 누락 목록에 남긴다.
5. 변환은 원본을 보존한 상태에서 다시 실행해도 같은 경로가 나오게 한다. 중복 제목은 원본 ID로 구분하고 글 간 링크를 새 주소로 변환한다. 본문 HTML은 스크립트·이벤트 속성·불필요한 외부 삽입을 제거하고 코드 블록, 표, 문단, 대체 텍스트를 유지한다.
6. 글 수를 원본과 대조한다. 공개 대상 전체의 HTTP 응답, 내부 링크, 이미지 로드, 누락 파일과 중복 경로를 검사한다. 오래된 글, 최신 글, 이미지가 많은 글과 모바일 본문을 사람이 표본 검수한다.
7. 가용한 백업이 오래된 경우 마지막 복원 가능 발행일과 누락 범위를 기록하고 추가 확보 자료만 별도 편입한다. 오래된 티스토리 URL이나 이미지 CDN이 살아 있어도 새 사이트의 영구 원본으로 가정하지 않는다.

## 5. 독립 화면 구성과 배포

- 권장 구성은 **Cloudflare Pages 정적 프론트 + 기존 Oracle API + 기존 GAS + 정적 글 아카이브**다. 전용 CMS나 새 DB는 초기 범위에 포함하지 않는다.
- 기존 skin.html의 티스토리 전용 치환자, 목록 루프, 글 렌더링, 관리자·방명록 마크업을 독립 진입점과 아카이브로 분리한다. 공통 JS/CSS·디자인 토큰·차트·NineHttp/NineAPI/NineUI를 재사용하고 로드 순서와 DOM 계약을 유지한다.
- 메뉴별 직접 URL, 쿼리스트링, 종목 코드, 새로고침, 뒤로가기, 모바일 탭을 검증한다. 정적 파일 404와 문서 라우트 404를 구분한다. 주요 글 경로는 사이트맵에 포함한다.
- 배포 디렉터리는 공개 파일 허용 목록으로 구성한다. 키, 환경 파일, DB, 원시 로그, 승인 파일, 거래 코드·운영 도구와 비공개 글이 산출물에 섞이지 않는지 검사한다. GitHub 연동 빌드에서 수행하고 PC에는 소스를 저장하지 않는다.
- Oracle의 HTTP CORS와 WebSocket Origin 검사를 각각 확인한다. 병행 기간에는 기존 사이트와 검증된 새 공개 Origin만 허용한다. 인증·요청 제한·TLS를 유지하고 브라우저 산출물에 API 비밀값을 넣지 않는다. GAS는 새 Origin에서 실제 호출·오류·캐시 동작을 검사한다.
- HTML은 변경 반영이 빠른 캐시 정책을 두고 버전이 붙은 정적 자산은 장기 캐시한다. 새 HTML과 자산은 같은 배포 단위로 올리고, 이전 배포가 참조하는 자산을 롤백 기간 동안 유지한다.
- 호스팅 장애 시 Oracle 정적 배포는 별도 가상 호스트와 릴리스 디렉터리로 구성한다. 업로드 완료·해시·HTTPS 검증 뒤 활성 릴리스 링크를 전환한다. 기존 API 프로세스의 장중 재시작을 전제로 하지 않는다.

## 6. 장비·비용·용량

| 항목 | 초기 기준 |
|---|---|
| 신규 물리 장비 | 0대. 공개 화면과 글을 정적으로 배포하고 기존 공개 API 사용 |
| Cloudflare Pages | 무료 플랜 후보. 공식 문서 기준 월 500빌드, 사이트당 20,000파일, 단일 자산 25MiB. 실제 글 포함 산출물로 재검증 |
| 도메인 | 기존 소유 도메인의 하위 주소를 쓰면 신규 등록 불필요. 신규 도메인은 등록·갱신 가격 확인 |
| 백업 | 글·이미지와 운영 백업의 총 용량, 사본 수, 보존 기간, 복구 다운로드 비용으로 별도 산정 |
| Oracle 현황 | 2026-11-11 조회 시 4 vCPU, RAM 약 24GB 중 가용 약 22GB, 루트 디스크 174GB 중 여유 146GB. 단일 시점 측정 |
| Oracle 교체 견적 | 공개 API·수집·DB까지 이전하는 경우 초기 검토 기준 4 vCPU, RAM 8~16GB, SSD 100GB 이상. DB 증가량·복원 임시 공간·백업·리전 지연·고정 IP 비용을 실제 측정 후 확정 |

장중 API 요청률, p95 응답시간, WS 동시 연결, CPU·메모리, 디스크 증가량을 기존 사이트와 병행 환경에서 기록한다. 배포 시점의 가격과 한도는 [Cloudflare Pages 공식 문서](https://developers.cloudflare.com/pages/platform/limits/)에서 다시 확인한다. 글 이미지가 한도를 넘으면 이미지 전용 저장소 또는 기존 정적 서버를 검토하고, 원본의 독립 백업을 유지한다.

## 7. 공개 전 검증과 전환

- [ ] 새 주소에서 HTTPS, 인증서 체인, DNS 레코드, HTTP→HTTPS, 혼합 콘텐츠 검증
- [ ] PC·모바일 홈, 국내·미국 종목판, 개별 차트, 검색기, 시장지표, 글 목록·본문·이미지 검증
- [ ] 주요 직접 URL과 쿼리, 404, 새로고침, 새 탭, 모바일 내비게이션 검증
- [ ] 장중 API 신선도, KRX/NXT 구분, 장외·휴장·결측 표기, 시세 기준시각 검증
- [ ] WS 연결·끊김·재연결·구독 복원, 백그라운드 탭 재활성화, 과도한 재요청 방지 확인
- [ ] GAS 위젯과 공급자 오류, API·GAS 장애 때 공개 화면의 안내 및 복구 확인
- [ ] 글·이미지 수와 누락 목록 승인, 사이트맵·canonical·검색 노출, 공개 산출물 보안 검사
- [ ] 자동매매 서비스·제어 경계와 별개임을 확인. 실계좌 API를 호출하거나 주문을 보내는 방식으로 검증하지 않음
- [ ] 직전 배포 복원, 기존 DNS 되돌리기, 상태 안내 페이지 공개를 연습

가능하면 거래일 한 세션을 병행 검증한다. 사전 검증 주소에는 검색 노출을 제한하고 공개 직전에 제한을 해제한다. 새 주소 공개 후 티스토리가 살아 있으면 이전 안내와 글별 새 링크를 게시한다. ghlee.tistory.com에 대한 DNS와 서버 리디렉션은 운영자가 직접 통제할 수 없으므로, 플랫폼 접근을 잃으면 새 사이트에서 옛 주소를 일괄 리디렉션할 수 있다고 가정하지 않는다. 공개 이후 주요 URL·오류율·WS·새 글 누락을 첫 장중과 장 마감 후 확인한다.

## 8. 롤백과 종료 조건

- 핵심 화면 장애, 시세 신선도 오표기, 개인 자료 노출, 광범위한 글·이미지 누락이 있으면 전환을 멈춘다. 노출 자료는 즉시 비공개로 전환하고 원인과 영향 범위를 확인한다.
- 프론트는 직전 정상 배포 ID나 릴리스 디렉터리로 되돌리고 HTML과 정적 자산을 함께 확인한다. DNS를 변경했다면 이전 레코드를 복원하고 TTL 동안 양쪽에서 도달 가능한 상태를 유지한다.
- 티스토리 복귀가 불가능하면 자체 도메인에 검증된 글·상태 안내를 유지하고 문제가 있는 기능만 닫는다. API와 GAS 설정을 수정했다면 독립적으로 복원하고 기존 Origin 연결을 검증한다.
- 전환 완료 기록에 실제 시각, 공개 주소, Git SHA, 배포 ID, 글·이미지 검수 수치, 알려진 누락, 담당자와 후속 일정, 마지막 정상 버전을 남긴다. 예산과 복구 목표의 실측값은 첫 훈련 후 갱신한다.

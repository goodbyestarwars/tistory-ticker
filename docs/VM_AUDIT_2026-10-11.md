# 운영 VM 보안·정리 점검 (2026-10-11)

읽기 전용 점검 후 안전한 항목만 조치했다. 서비스 재시작·재부팅 없음. 키·토큰 값은 보지 않고 이름과 권한만 확인했다.

## 조치한 것

| 항목 | 전 → 후 |
|---|---|
| 앱 폴더 `.env`(API 키·세션 비밀 보관) 권한 | 664(다른 계정 읽기 가능) → **600** |
| 백업 폴더 권한(사용자 데이터가 든 DB 사본) | 755/644 → **700/600** |
| systemd 저널 | 1.0GB → 173MB (`journalctl --vacuum-size=200M`) |
| apt 캐시 | 112MB 삭제 |
| Ops Agent가 회전해 둔 2026-08-02자 로그 | 419MB → 0 (사용 중이라 삭제 대신 비움) |
| 디스크 | 사용 11GB(38%) → 9.1GB(33%) |

조치 뒤 `kiwoom-api` 서비스 active, 로컬·공개 `/health` 200, 배포·스캔 타이머 active.

## 확인했으나 조치하지 않은 것 (판단 필요)

1. **방화벽 8080 전 세계 개방**: GAS가 `http://{VM IP}:8080`을 호출하는 구조라 닫으면 GAS가 끊긴다. 평문 HTTP + `X-API-Key` 방식이라 키가 네트워크에 평문으로 흐른다. 개선안: GAS→VM을 HTTPS(`goodbyestar.cloud`)로 바꾼 뒤 8080 방화벽 제거.
2. **RDP(3389) 전 세계 개방**: 리눅스 VM이라 서비스는 없다. 불필요한 규칙이므로 삭제 권장(영향 없음). `default-allow-rdp`.
3. **`.env` 22행에 `y` 한 줄**: 잘못 붙은 문자로 보인다. 값은 없고 로드 경고만 낼 수 있다. 앱 설정 파일이라 직접 수정하지 않았다 — 사용자가 확인 후 삭제.
4. **재부팅 대기**: `/var/run/reboot-required` 존재, 업그레이드 가능 패키지 39개, 커널 2개 설치(구버전 `7.0.0-1011`). 이전 인수인계에 "GCP 장애 중 VM 중지·재시작 금지" 기록이 있어 건드리지 않았다. 재부팅 후 `apt autoremove`로 구커널 정리.
5. **백업 보관**: `backups/` 727MB. `ohlc_snapshot_20260808...`(207MB)은 두 달 지난 유일한 사본이고 뉴스 DB 백업은 9/26이 마지막이다(백업이 계속 도는지 확인 필요). 디스크 여유가 충분(19GB)해 삭제하지 않았다. 보관 개수·주기 정책을 정할 것.
6. **계정**: 로그인 가능한 로컬 계정 3개(`ubuntu`, 앱 사용자, 개인 계정). `ubuntu`는 cloud-init 기본 계정으로 NOPASSWD sudo. 쓰지 않으면 키 제거를 검토. SSH는 비밀번호 로그인 꺼짐(양호).
7. **Cloud Logging 수집기(Ops Agent)** 가 계속 로그를 보내고 있다. 유료 전환 상태이므로 월 수집량(무료 한도 50GiB)을 결제 보고서에서 확인할 것.

## 이상 없음

- 저널·앱 로그에서 키·Bearer 토큰 형태 문자열 0건. `.bash_history` 없음.
- 저장소 추적 파일에서 하드코딩된 키 없음. 주석에 VM 공인 IP 1건(`naver_news.py`, 공개 IP라 위험은 낮으나 필요 없으면 제거).
- 앱 로그(`deploy.log`, `latency_monitor.log` 등)는 각 1MB 미만, 저널·nginx 등은 logrotate 대상.

## 후속 조치 (같은 날)

- 방화벽 `default-allow-rdp`(3389) 삭제. 남은 개방 포트: 22(SSH, 비밀번호 로그인 꺼짐)·80·443·8080(GAS용).
- `.env` 22행의 잘못 붙은 `y` 삭제(원본은 root 전용 위치에 백업, 권한 600 유지).
- `test/test_volume_breakout_probe.py` 삭제 — 9/22에 없앤 probe 기능의 테스트였다.
- **밀린 장외 유지보수 발견**: 마지막 정상 실행이 2026-09-27이고 이후 `maintenance.log`에 "스캔 실행 중 - 장외 유지보수는 다음 회차로 미룸"이 532회 쌓였다. 즉 03~05시 창에서 `.scan_serial.lock`이 매번 잡혀 있어 DB 백업·보존 정리·로그 정리가 2주 멈춰 있었다.
  잠금이 비어 있는 일요일 아침에 같은 명령(`flock -n` + `nice`/`ionice`)으로 수동 실행했다 → 45초 안에 exit 0, 새 `news_momentum` 백업 생성, 서비스·`/health` 정상.
  원인(누가 잠금을 쥐는지)은 현재 상태에서는 재현되지 않아 확정하지 못했다. `deploy_check.sh`에 미룰 때 잠금 보유 프로세스를 로그에 남기는 진단 한 줄을 추가했다(판정 로직 불변). 며칠 뒤 `maintenance.log`의 `lock holder:` 줄로 원인을 확인할 것.
- 같은 로그 정리가 주말에 `auth.log`·`syslog`를 `truncate`로 비운다(유지보수 설계). SSH 접속 기록이 매주 사라지므로 보안 감사를 원하면 logrotate 보관으로 바꾸는 것을 검토.

## 하지 않은 것과 이유

- **8080 방화벽 닫기**: GAS가 `http://{VM IP}:8080`을 쓴다. GAS 스크립트 속성 `KIWOOM_VM_URL`을 `https://goodbyestar.cloud`로 바꾸는 것은 GAS 관리 화면에서만 가능해(수동) 먼저 바꾼 뒤 닫아야 한다.
- **재부팅·패키지 업그레이드**: 이전 GCP 장애 기록(VM 중지·재시작 시 기동 실패 가능) 때문에 보류. 재부팅 대기 상태이며 업그레이드 가능 패키지 39개.
- **`ubuntu` 계정 키 제거**: 사용 여부를 확인할 수 없어 보류.
- **백업 삭제**: 보관은 이미 DB별 7개 유지(`maintenance.py keep=7`)라 정책이 있다. 08-08 `ohlc_snapshot` 백업은 정기 백업 대상이 아닌 유일한 사본이라 보존.

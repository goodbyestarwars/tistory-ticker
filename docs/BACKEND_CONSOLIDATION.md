# 백엔드 일원화 방향 — GAS 폐기, VM으로 수렴

작성 2026-08-31. 이 문서는 "왜 그렇게 가는가"와 "어떤 순서로 가는가"를 고정한다.
개별 작업 내역은 `docs/WORK_HISTORY.md`, 구조 현황은 `ARCHITECTURE.md`를 본다.

## 1. 문제 — 백엔드가 둘이고, 느린 쪽이 앞에 있다

`ARCHITECTURE.md`에 적힌 대로 브라우저가 직접 부르는 백엔드가 **GAS와 VM 2군데**다.
문제는 나뉘어 있다는 것 자체보다, **느린 쪽(GAS)이 빠른 쪽(VM) 앞에 서 있다**는 것이다.

2026-08-31 홈 첫 화면 실측(모바일 375px, 브라우저 안 기준):

| 호출 | 응답 |
|---|---|
| VM `/futures` | 306ms |
| VM `/investor-trend` ×2 | 301ms |
| VM `/market-board` | 262ms |
| VM `/watchlist`, `/auth/google/me` | 241ms |
| **GAS `?bubble=1`** | **3,708ms** |
| **GAS `?marketTemp=1`** | **7,102ms** |

VM 호출은 전부 1.34초에 끝나는데 **마지막 데이터는 7.9초에 도착한다**(load 이벤트
1.16초의 6.8초 뒤). 즉 홈의 체감 속도는 전적으로 GAS가 결정한다.
curl 단독 측정으로도 GAS는 캐시 히트 1.6~2.7초, 미스 7초+다. 브라우저 안에서는
다른 요청과 경쟁해 더 나빠진다.

## 2. 결정적 근거 — GAS는 이미 VM의 중간상이 됐다

느린 것보다 중요한 건 **토폴로지가 거꾸로**라는 점이다. GAS 코드가 스스로 VM을 부른다:

- `fetchKofiaMarketFromVm_()` → `kiwoomVmFetch_('/kofia-market?days=30')`
  (`getMarketTemp()`가 신용융자 점수를 낼 때 사용)
- `getFundamentals_()` → `kiwoomVmFetch_('/quote?code=')` 를 받아 필드만 재포장

지금 데이터 흐름:

```
브라우저 → GAS(1.6~7초) → VM(0.25초) + 외부(네이버 등)
```

여기서 GAS를 빼면:

```
브라우저 → VM(0.25초) + 외부
```

**한 홉이 통째로 사라진다.** GAS가 하는 일 중 상당수는 이미 VM이 가진 데이터의 재포장이다.

부수 근거:
- VM 엔드포인트가 이미 **50개**로 대부분 도메인을 덮는다. GAS에 남은 액션은 24개.
- 같은 도메인이 양쪽에 중복 존재한다: `action=foreignFlow` ↔ `/foreign-flow/{code}`,
  `action=fundamentals` ↔ `/fundamentals/{code}`.
- 이미 한 번 같은 판단을 내린 적이 있다 — `js/foreign-flow.js` 주석:
  "2026-07-13: GAS `?action=investorFlow` 경유 방식은 **폐기됨** - GAS→VM 구간이
  간헐적으로 통째로 막히는 원인 불명 현상 때문에 브라우저가 VM을 직접 호출".
  **마이그레이션은 이미 시작됐고 중간에 멈춰 있다.**

## 3. 방향

> **GAS를 새 기능의 경유지로 쓰지 않는다. 남은 GAS 액션은 VM으로 옮기고, 옮긴 것은
> GAS에서 지운다. 최종 목표는 브라우저 → VM 단일 경로다.**

명시적으로 **하지 않을 것**:
- **VM이 GAS를 프록시하고 캐시하는 방식은 쓰지 않는다.** 응답은 빨라지지만 GAS 의존이
  영구화되고, GAS↔VM 구간(이미 장애 이력이 있는 링크)이 상시 경로가 된다. 증상만 덮는
  땜질이다.
- GAS 캐시 TTL을 늘리는 식의 조정도 마찬가지다. 미스 때 사용자가 7초를 무는 구조는
  그대로 남는다.

## 4. 시장 전체 지표는 요청 시점에 계산하지 않는다

`getMarketTemp()`가 느린 근본 이유는 GAS라서가 아니라 **요청을 받고 나서 전종목 시세를
긁어 점수를 매기기 때문**이다. 증시온도·시가총액 버블은 방문자마다 달라지지 않는
**시장 전체 지표**다. 요청 경로에서 계산할 이유가 없다.

VM으로 옮길 때는 그대로 옮기지 말고 **백그라운드 주기 계산 + 즉시 서빙**으로 바꾼다.
이 저장소에 이미 같은 패턴이 있다:
- 스캔 타이머(`daily_scan` 16:00, `strategy_scan` 16:20, `angle_momentum_scan` 16:25 …)
- 상시 폴러(`foreign_futures.start_background()`, `domestic_futures`, `bond_yield` …)

그러면 방문자 응답은 캐시 읽기 수준(수십 ms)이 되고, 워머 같은 보조 장치도 필요 없다.

## 5. 순서

이득이 큰 것부터, 위험이 낮은 것부터 섞어서 간다.

| 단계 | 대상 | 성격 | 위험 |
|---|---|---|---|
| 1 | `marketTemp=1` → VM `/market-temp` (백그라운드 계산) | 홈 7.1초 제거 | **중** - 배점 이식이 값을 바꾸면 안 됨 |
| 2 | `bubble=1` → VM `/marketcap-bubble` | 홈 3.7초 제거 | 중 |
| 3 | `action=fundamentals` → 이미 있는 `/fundamentals/{code}` | 홉 제거만 | 낮 |
| 4 | `action=foreignFlow` → 이미 있는 `/foreign-flow/{code}` | 중복 제거 | 낮 |
| 5 | 나머지 액션(AI 해설 계열 등) 개별 판단 | | |

각 단계 공통 규칙:
1. VM에 새 경로를 만들고 **프론트는 아직 바꾸지 않는다.**
2. 같은 입력으로 GAS 응답과 VM 응답을 **비교하는 테스트**를 먼저 통과시킨다.
   특히 1·2단계는 화면에 뜨는 숫자(증시온도 점수 등)가 달라지면 안 된다.
3. 일치가 확인된 뒤 프론트를 VM으로 돌린다.
4. 한 사이클 운영해 문제없으면 **GAS에서 해당 액션을 지운다**(안 지우면 중복이 남아
   다음 사람이 어느 쪽이 진짜인지 모른다 - 지금 `foreignFlow`가 그 상태다).

## 6. GAS를 계속 둘 수도 있는 것

전부 옮기는 게 목적이 아니다. 아래는 남겨도 되는 후보다. 옮길 이유가 생기기 전까지 둔다.
- Google 계정·시트에 붙어야만 하는 작업
- 호출 빈도가 낮고 첫 화면 경로가 아닌 AI 해설류(`marketTempBriefing`, `priceReason` 등)
  단, 이들이 내부적으로 `getMarketTemp()` 같은 무거운 함수를 다시 부르는지는 확인할 것.

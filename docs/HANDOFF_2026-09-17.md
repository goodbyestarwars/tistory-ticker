## 4. 오늘 해결한 장애 두 건

### (1) 5분마다 API 재시작 루프 (#473)
`post_deploy_check.py`의 `/health` 대기가 "5초×20회 = 실측 25초"였는데 FastAPI 기동은
**41~64초**였다. 매번 실패 → `set -e`가 SHA 기록 앞에서 끊음 → 5분 뒤 같은 커밋 재배포.
마감 시각(180초) 기준으로 바꿨고, 실패해도 SHA는 남긴다. 이후 재시작 동반 배포 2회 모두
`post_check=ok` 확인.

### (2) 07:30 리퍼가 실제로는 유닛을 못 멈추고 있었음 (#476)
첫 실전에서 `kiwoom-batch`가 2,276/3,913 진행 중이었는데 "실행 중인 스캔 없음"을 찍고 지나갔다.
스캔 유닛이 전부 `Type=oneshot`이라 도는 동안 ActiveState가 `active`가 아니라 **`activating`**
이고, `systemctl is-active --quiet`가 거짓을 돌려줬다. 마감을 지킨 건 뒤의 `fuser -k`였고
그 경로로 죽은 유닛은 `failed`로 남는다. ActiveState를 직접 읽도록 고쳤다.

## 6. ⚠️ 열려 있는 문제 — 실시간 시세가 특정 종목에 안 온다

사용자 보고: "이 부분 또 websocket 이 안되는거 같다" (종목 검색에서 대한광통신 010170).

### 확인된 사실 (전부 실측)

**WebSocket 인프라는 정상이다.**

| 경로 | 결과 |
|---|---|
| 앱 직접 `http://127.0.0.1:8080/ws/quotes?codes=010170` (Origin 붙임) | `101 Switching Protocols` |
| nginx 거쳐 외부 `wss://goodbyestar.cloud/...` | `101` + `{"type":"ready"}` + `{"type":"coverage","live":["010170"]}` |
| 브라우저(ghlee.tistory.com 오리진)에서 직접 소켓 | 698ms 만에 open |

**문제는 종목별 틱이다.** 소켓 하나에 세 종목을 같이 걸고 12초 관찰:

| 종목 | 받은 틱 |
|---|---|
| 삼성전자 005930 | 63틱 |
| SK하이닉스 000660 | 42틱 |
| **대한광통신 010170** | **0틱** |

그런데 서버는 `coverage: live:["010170"]`이라고 답한다. 화면은 "실시간 받는 중"인 줄 알고
기다리므로 값이 멈춘다. 사용자 화면에서 상단 요약 16,260원 / 호가창 16,210원으로 갈린 게 이것.

**서버 상태(`GET /health/realtime`)에서 의심 가는 대목:**
```
registered 40 / maxRegistrations 40    <- 등록 슬롯 포화
optionsBudget 10                        <- 코스피200 옵션이 10자리 상시 점유
droppedCount 38                         <- 드롭된 건 전부 옵션(H0IOCNT0/H0IOASP0)
kiwoom {running:.., connected:false}    <- 키움 허브는 폴백 경로라 평소 꺼져 있음(정상)
```

`kis_ws_hub.py`의 `_desired()`를 보면 **같은 우선순위(`PRIORITY_QUOTES`) 안에서는
`_key_order`(먼저 등록된 순)로 자리를 지킨다.** 홈 화면 카드가 선점하고 있으면 방금 검색해서
연 종목이 40번째 밖으로 밀린다. 단타에서는 정확히 반대여야 한다.

### 아직 확정 못 한 것
드롭 목록에는 **옵션만** 찍혀 있고 010170은 없다. 그런데도 틱이 안 온다.
"등록됐다고 답하는데 데이터는 안 오는" 구간이 남아 있다. **여기가 다음 사람이 팔 자리다.**

### 조사하면서 틀렸던 것 (같은 함정 피하라고 남김)
- 브라우저로 페이지를 열었을 때 소켓이 0개라 "프론트가 소켓을 안 연다"고 판단했는데 **틀렸다.**
  `order-book.js`의 `startRealtimeQuote`는 `document.hidden`이면 소켓을 안 연다. 브라우저 창이
  숨어 있으면 정상적으로 안 연다. **`document.hidden`을 먼저 확인할 것.**
- `wss://.../ws/quotes`는 **`?codes=`가 없으면 거부**된다(403 → 브라우저에는 1006). 코드 없이
  열어보고 "서버가 죽었다"고 판단하지 말 것.
- Origin이 `https://ghlee.tistory.com`이 아니면 accept 전에 닫는다(→ 403). curl로 칠 때
  `-H Origin:https://ghlee.tistory.com`을 반드시 붙인다.

### 소켓을 여는 주체 (헷갈리기 쉬움)
종목 상세 화면에서 소켓은 **`js/order-book.js`의 `#order-book` 위젯 하나만** 연다.
상단 요약(`js/stock-search.js`)은 그 위젯의 `opts.onQuote` 콜백을 받아 쓴다. 2026-08-05에
소켓 2개가 뜨면서 값이 어긋나 일부러 하나로 합친 구조다. **다시 쪼개지 말 것.**

### 제안한 수정 방향 (아직 승인 안 받음)
1. **종목 단위 등록 추적 로깅** — 어떤 키가 실제로 KIS에 등록 프레임을 보냈고 응답이 뭐였는지.
   지금은 집계만 있어 010170 하나를 따라갈 수 없다. **이게 1번이다.**
2. **"지금 보고 있는 종목" 우선순위 티어** — 검색·상세로 연 종목을 배경 카드 구독보다 앞세운다.
3. **`coverage` 정직화** — 자리를 못 받았으면 `live`가 아니라 `delayed`로 답한다. REST 폴백
   (`rest_quote_fallback.py`)이 이미 있어서, 그렇게만 해도 화면이 멈추지 않고 지연 시세로 채워진다.

### 이미 적용한 완화 - 옵션 실시간 끔 (#481)
`option_flow.py`가 **코스피200 옵션 콜/풋 상위 각 10계약**을 실시간 등록해
(`_realtime_rows(calls, puts, limit=10)`) 40자리 중 10자리를 상시 먹고 있었다.

사용자 확인: **"옵션은 아직 보조로 내가 넣으라고 한건데, 이건 실시간 아니여도 된다."**

그래서 실시간 구독을 **기본 꺼짐**으로 바꿨다(`realtime_ws_enabled()`, `OPTION_REALTIME_WS=1`로
되돌릴 수 있음). 이미 있던 순수 REST 경로(`_poll_loop` → `refresh_option_flow` 5분)로 태웠으므로
콜/풋 숫자는 그대로 나온다. `/option-flow`의 `websocket` 플래그도 false로 답해
`js/kospi-futures.js`의 문구가 "WS 실시간 보강" → "REST 스냅샷"으로 정직하게 바뀐다.

**효과: 개별 종목이 쓸 수 있는 실시간 자리가 30 → 40개.** 다만 이건 완화지 원인 해결이 아니다.
위 1~3번(등록 추적 로깅 / 보고 있는 종목 우선순위 / coverage 정직화)은 그대로 남아 있다.

### (3) 거래량 돌파 09:05 관측 (#480, 내일 아침 09:05)

않는다. 앞당기려면 문턱을 같이 낮춰야 하고, 그 값을 재려고 관측 패스를 넣은 것이다.

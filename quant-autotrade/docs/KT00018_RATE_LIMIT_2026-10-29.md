# kt00018 Windows 공통 유량제어 — 2026-10-29

상태: 작업 브랜치 코드·오프라인 검증. PC 운영본 설치, master 병합, VM 배포, 프로세스 재시작은 미승인·미실행.
사용자가 전달한 2026-10-29 18:00 KST 이후 초당 3회 기준을 요구사항으로 삼았다. 공지 원문은 이번 공개 웹 검색에서 독립 확인하지 못했다.

## 변경 범위

- local_bot/kiwoom_balance_gate.py: 두 클라이언트가 공유하는 kt00018 전용 OS 파일 잠금.
- local_bot/kiwoom.py, live_kiwoom.py: 실제 전송 바로 앞에서 공통 gate 사용. 다른 조회 API의 기존 간격은 유지.
- kiwoom.py만 Lock → RLock: HTTP 인증 실패의 재귀 call 교착 수정. live_kiwoom.py는 이미 RLock.
- 두 클라이언트 모두 kt100* 주문의 인증 오류 자동 재전송 금지. 일반 조회의 인증 갱신은 기존 1회 유지.
- 잔고 성공 코드·목록·수량·보유 종목코드를 검증한다. 연속조회 헤더 cont-yn=Y인 부분 잔고도 예외로 차단한다. 추가 페이지 자동 수집은 하지 않는다.
- runner/engine/ninepay_trade/신호 수신기, 매매 조건·예산·손절·익절·후보 순위는 변경하지 않는다.

## 잠금 계약과 재사용 판단

기존 procguard.InstanceLock은 PID/mtime 기반 단일 봇 실행 보호이며 API 전송의 프로세스 상호배제용이 아니다. 기존 클라이언트의 threading lock 역시 프로세스별이다. 따라서 한 공통 모듈로 두 클라이언트가 함께 쓰는 OS 잠금을 추가했다. 별도 상시 서비스나 DB가 필요하지 않다.

Windows 기본 공통 위치는 %PROGRAMDATA%/9Pay/kiwoom-kt00018.lock이며 체크아웃·키별로 나누지 않는다. 잠금 획득 후 monotonic 시계로 최소 0.55초 대기하고 urlopen 및 응답 처리 종료까지 잠금을 유지한다. 시작 간격은 최소 0.55초+이전 요청 처리시간으로, 참여 프로세스 합산 임의의 1초 구간 최대 2회다. 첫 호출도 대기한다. 실패와 인증 재시도도 같은 gate에 진입한다.

영속 타임스탬프가 없어 벽시계 변경과 오래된 상태 복구가 필요 없다. 소유 프로세스가 죽으면 OS가 잠금을 해제하고 다음 소유자가 다시 0.55초를 기다린다. 잠금 경합 최대 대기는 30초이며 파일/권한/잠금 오류는 요청을 보내지 않고 예외로 종료한다. 운영 중 lock 파일 삭제·교체는 금지한다. 설치 계정 간 ACL은 적용 전 확인한다. Linux flock 분기는 이번 Windows 실행에서 검증하지 않았다.

공통 모듈을 사용하지 않는 MCP/다른 프로그램/다른 PC·VM은 이 제한에 참여하지 않는다. 전체 계정 호출 제한까지 보장한다고 주장하지 않는다. OS에서의 전송 시작 간격 검증이며 증권사 수신 시각·네트워크 큐 지연은 실측하지 않았다.

## 안전 영향

잔고 예외는 engine/9Pay 주문 예약 이전에 전파돼 신규 주문과 잘못된 포지션 청산 처리를 막는다. 봇은 기존 실패 경로로 판단을 중단한다. runner는 RuntimeError에 기존 ERROR_RuntimeError 종료 정책을 유지한다. 잠금 경합/느린 응답으로 청산 점검이 지연될 수 있으므로 속도를 위해 우회하거나 이전 잔고를 거래 판단에 사용하지 않는다. 불확실 주문·중복 방지 장부와 전략 코드는 변경하지 않았다.

## 오프라인 검증

Windows Python 3.14에서 외부 socket 연결을 차단하고 브로커 호출을 fake/mock으로 대체했다. 로컬 Telegram fake HTTP 서버 테스트만 loopback 통신을 허용한다.
최종 local_bot 전체 252개 통과(89.805초), 운영 소스 복사본의 신규 안전성 테스트 14개 통과(15.935초). 신규 test_balance_gate.py는 연속·3개 spawn 프로세스 합산·비정상 종료·예외/재시도·시계·권한/잠금 실패·인증 교착·주문 무재전송·잘못된/부분 잔고·9Pay 및 기존 엔진 신규 주문 차단·포지션 보존·runner 순서와 불확실 주문 정지를 검증한다.

운영 Python 코드만 복사한 별도 폴더에서도 패치 검증을 실행했다. 운영본 동봉 기존 테스트 60개는 수정 전/후 동일한 실패 12개(8 assertion failures + 4 errors): 누락된 설치 제외 목록 fixture 2개, 과거 진입시간 가정 1개, 오래된 봇 테스트 9개다. 이번 작업에서 운영 전략이나 옛 테스트를 바꾸어 통과시키지 않았다.

## 운영 반영 계획 — 별도 승인 필요

1. 장외 유지보수 창에서 미체결/불확실 주문과 운영 상태를 담당자가 확인한다. 현재 조회 API 통합 테스트는 승인되지 않았다.
2. 운영 소스와 예약 작업 XML을 별도 로컬 보관하고 3개 대상 파일의 전/후 SHA256을 기록한다. 승인 파일/STOP/환경설정/장부는 변경하지 않는다.
3. 봇과 runner를 모두 같은 버전으로 반영해야 한다. 패치 대상은 kiwoom_balance_gate.py, kiwoom.py, live_kiwoom.py 세 파일뿐이다. 일반 install_bot.ps1는 다른 코드와 스케줄·재시작까지 다루므로 이번 적용에 사용하지 않는다.
4. 공통 잠금 위치/권한·오프라인 테스트·구문을 검증한다. --check도 실제 토큰/잔고를 호출하므로 별도 API 승인 전에는 실행하지 않는다.
5. 실행 중인 봇은 import한 이전 코드를 계속 쓰므로 승인된 재시작이 필요하다. runner는 다음 예약 실행에서 새 코드 로드(실행 중이라면 별도 승인된 재시작). 스케줄 변경·수동 --run은 하지 않는다.
6. 실패 시 승인된 유지보수 절차에서 백업한 두 클라이언트를 복원한다. 새 모듈은 import되지 않으면 비활성이다. 롤백은 기존 합산 유량 위험도 복원하므로 실거래 재개 여부를 재판단한다. 자동 재개/주문 재전송은 금지한다.

현재 PC와 master의 runner/engine/신호 정책 차이를 이번 패치와 묶어 갱신하지 않는다. 최신 runner 전면 설치는 별도 정책 검토·승인 대상이다.
